## 使用故事

用户在一份较大的 `.prg` 上继续编辑，按 **Ctrl+S** 保存。期望保存完成后立刻继续工作；实际是：界面数秒到数十秒无响应，无法切换标签、无法操作，等待一段时间后才恢复。

## 量化口径

分段计时（每段独立毫秒）：

| 段                                      | 位置                                                         |
| --------------------------------------- | ------------------------------------------------------------ |
| `serialize`                             | `Project.getFileContent` 首行                                |
| `msgpack.encode`                        | stage / tags / reference / metadata 分别计时                 |
| zip 各 entry                            | `writer.add` 逐项计时（stage / tags / reference / metadata / |
| readme / 每个 attachments / thumbnail） |
| `uwriter.getData`                       | 全量拼接                                                     |
| 缩略图                                  | `generateThumbnail` 全段                                     |
| 落盘                                    | `fs.write`（含 Tauri IPC）                                   |
| `clearHistory`                          | 保存后的历史清理                                             |
| 最近文件                                | `RecentFileManager.addRecentFileByUri`                       |
| **主线程阻塞窗口**                      | 用 `requestAnimationFrame` 间隔推算「最长一次无响应窗口」    |

规模口径：实体数、关联数、附件数、附件总字节、`serialize` 后字节数、zip 后字节数。

输出方式：

1. 追加写入应用缓存目录（`appCacheDir()`）下的 `save-timing.log`，agent 直接读文件取证；
2. 保存完成后对话框展示「总耗时 + 前三段 + 规模口径」，用户可见，便于口头反馈。

基准来源：

1. **离线**：仓库内 vitest/node 基准（合成规模 N=1k / 5k / 20k；若用户提供真实 `.prg` 路径，直接在真实文件上跑）；
2. **应用内**：用户在大工程上复现 1 次 Ctrl+S（同时静置观察是否存在周期性冻结）。

## 关键决策

| 编号 | 决策                                                                                                                                                           | 理由 / 反例                                                                                                           |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| D1'  | 第一轮 D1「不引入 Worker」**作废**：`msgpack.encode` + zip（+ md5）属纯数据变换，允许移入 Worker                                                               | 反例：`serialize` 依赖**活动对象图**，搬进 Worker 前必须转纯数据，等于多一次全量拷贝，可能更慢 → serialize 留在主线程 |
| D2'  | 若 `serialize` 被证实为主导：走「**分片让出**」（每 K 个对象 await 一次宏任务），不搬 Worker                                                                   | 反例：分片会让总耗时略增（可接受）；不处理就只能整段卡死（不可接受）                                                  |
| D3'  | 附件（`attachments/*`）单独计量；只有附件字节数占比显著时才处理（未变化附件跳过重写 / 保存前提示附件体积）                                                     | 反例：无脑缓存附件会导致 zip 内容与磁盘不一致                                                                         |
| D4'  | 周期性重活一并计量并处理：`AutoSaveBackupService.autoBackup` 的 `stageHash`（全量 serialize + encode + md5，**默认开启**、间隔 600s）与 `autoSave`（无防重入） | 反例：只修 Ctrl+S 会漏掉「放置不动也周期性冻结」；与用户「大工程会卡死」的整体体感可能同源                            |
| D5'  | 埋点是**临时**的，取证完成后收敛（默认关闭或整段移除），不长期留在保存路径                                                                                     | 反例：长期埋点在保存路径写日志会引入新的 IO 与卡顿                                                                    |
| D6'  | 第一轮改动保留；其中「大工程不再更新缩略图」是行为变化，需用户确认可接受（若不接受，改为保存后空闲时段异步补写）                                               | 反例：取消降级会把缩略图重新拉回保存主路径                                                                            |
| D7'  | 若各段耗时合计**远小于**实际冻结时长，则判定「不在保存链路」，转入保存后链路（IPC / 落盘 / 重渲染 / 事件监听）二次定位，不再盲改保存代码                       | 反例：继续在保存链路上做无据优化（第一轮的教训）                                                                      |

## 候选削减清单（按数据选用，不预设取舍）

1. `encode` + zip + md5 → **Worker**（主线程只留 serialize 与落盘）。
2. `serialize` → **分片让出**（每 K 个对象 await 一次宏任务）。
3. `serialize` **常数成本**：数字字段的 `toFixed(2)` 字符串化、路径字符串拼接（需先证明占比）。
4. **附件**：按内容哈希跳过未变化附件；或保存前提示附件体积。
5. **落盘**：分块/流式写（若 `fs.write` 的 IPC 传输是大头；若 plugin-fs 能力不足需单独立项）。
6. **周期性**：`stageHash` 改用 `StageManager.stageRevision` 比较（env-hang 已引入该字段）；`autoSave` 补防重入与「保存中」反馈。
7. **缩略图**：保存后空闲时段异步生成（仅当用户不接受陈旧缩略图）。

## 术语表（G2）

| 术语           | 定义                                                                      |
| -------------- | ------------------------------------------------------------------------- |
| 卡死           | 主线程被同步工作占满，>1s 内无输入响应与重绘                              |
| 主线程阻塞窗口 | 两次 `requestAnimationFrame` 之间的实际间隔，用于量化「最长无响应时长」   |
| 舞台快照       | `serialize(project.stage)` 产出的纯数据（非对象引用）                     |
| 分片让出       | 把长同步任务切成若干片，片间 await 一次宏任务，让浏览器插空处理输入与重绘 |
| 附件增量       | 只重写内容发生变化的 `attachments/*` 条目                                 |

## 方案自检（G4）

1. **假设清单**：serialize / 编码 / zip / 落盘谁是大头 → **未量化**，本轮第 1、2、3 项任务先取证；不再基于假设改代码（第一轮教训）。仍存在的假设：大工程规模落在哪个量级（由埋点给出）。
2. **遗漏场景**：草稿/协作保存路径（`saveAs`）；自动保存与自动备份（`includeThumbnail: false` 路径）；多标签同时保存；附件参与打包；缩略图被跳过后的陈旧问题。
3. **前后矛盾**：无（第一轮 D1 已显式作废并说明原因）。
4. **术语一致性**：统一使用「主线程阻塞窗口」「舞台快照」「分片让出」。
5. **外部依赖**：Worker 由 Vite 原生支持（`new Worker(new URL("./x.ts", import.meta.url), { type: "module" })`），无需新增依赖；Tauri `plugin-fs` 是否支持分块写待确认（若不足，改 Rust 侧命令需单独立项）。
6. **回退路径**：埋点可整段移除；Worker 化保留主线程同步实现作为回退分支；分片序列化保留原 `serialize` 路径（按规模阈值或开关启用）。
