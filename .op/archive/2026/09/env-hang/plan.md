# 方案：当前环境卡死问题处理（env-hang）

## 使用故事

- 使用场景：本机 PC 端 Project Graph，长时间使用（打开/切换工程、编辑、开着大纲等子窗口），随后离开一段时间（放置不操作），回来时整个应用无法操作，只能关闭重开。
- 使用角色：图编辑者（日常使用者）；性能/稳定性回归维护者。
- 使用时机：单次会话持续使用数十分钟以上；期间打开过多个工程或子窗口。
- 前置条件：至少打开/关闭过一个工程（触发 Project 生命周期）；可选的长时间编辑（历史快照累积）。
- 使用过程：
  1. 【PC】图编辑者打开工程 A 编辑一段时间，再打开/切换到工程 B（或关闭 A）。
  2. 【PC】图编辑者继续使用，期间可能打开大纲等子窗口。
  3. 【PC】图编辑者离开电脑一段时间（放置不操作）。
  4. 【PC】图编辑者回来后点击/按键，发现界面完全无响应，只能关闭应用重开。

## 现象（用户确认口径）

> 「使用一段时间后会出现假死的情况，然后无法进行任何操作了，这不是突然的，而是操作一段时间后，放置不操作，过段时间再去操作时，发现用不了了，需要关闭后重新打开。」

即：**长会话 + 累积型退化 + 空闲后暴露**，而非某一步操作即刻卡死。因此排查方向从「单次操作的复杂度」转向**只增不减的资源积累与常驻后台开销**。

## 方案概述

针对「累积型退化导致空闲后假死」，按**先止损、再降常驻开销**的顺序做等价修复，不改变任何交互行为：

1. **让旧工程真正可被回收（根治 D1 / D2）**
   - `Canvas`：把 `keydown`/`keyup`/`blur` 与元素上的 `mousemove`/`focus` 处理器保存为字段，`dispose()` 中用**同一引用** `removeEventListener`（连同 `resizeObserver.disconnect()` 与 `element.remove()`）。
   - `Controller.dispose()`：注册与解绑使用同一份已绑定引用（字段化），修掉 `.bind(this)` 造成的解绑失败。
   - 效果：项目关闭/切换后不再钉住旧 Project，内存不再随会话内「打开过的工程数」单调增长。
2. **消除常驻的整表序列化轮询（D3）**
   - 在 `StageManager` 暴露 O(1) 的舞台版本号（`updateReferences()` 与索引重建时递增；读取时经既有廉价指纹 `ensure()` 保证新鲜）。
   - `OutlineWindow` 的 300ms 轮询改为比较该版本号（O(1)），只在版本变化时执行原有的 `refresh()`；不再调用 `stageHash`。
   - `stageHash` 保留给 `AutoSaveBackupService`（那里需要「内容是否变化」的语义，频率是分钟级）。
3. **核验并顺带修 D4**：核实 `CollabTransport.pingTimer` 是否有清理、`MouseLocation.init()` 是否可能重复注册；确认是泄漏则按同一手法修（无证据则只记录、不改）。
4. **确定性回归**：用「解绑引用相等」「监听器计数不增」「版本号语义」三类断言守住，不依赖计时。

## 关键决策

| #   | 决策                                                     | 理由                                                                                                                                               |
| --- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 先修生命周期泄漏，再谈微优化                             | D1/D2 是唯一的**无上限**增长源（随会话内工程数增长），与「用一段时间后假死」直接对应；D3 是常驻开销                                                |
| 2   | `OutlineWindow` 用版本号替换哈希轮询，而非降低轮询频率   | 降频只是减轻，语义不变；版本号把「内容是否变化」的判定从 O(N) 序列化降为 O(1) 比较，且能命中所有舞台结构性变更（含既有 `updateReferences()` 触发） |
| 3   | `stageHash` 不删除，只收回给分钟级的备份路径             | 备份需要「内容变化」的强语义（哈希），删除会改变备份行为                                                                                           |
| 4   | 监听器修复采用「字段化已绑定引用」而非 `AbortController` | 与现有代码风格一致、改动面最小；`AbortController` 需要一次性重写注册段，风险更大                                                                   |
| 5   | 历史快照的内存上限（按字节裁剪）不在本轮                 | 属设计变更（影响撤销粒度/内存取舍），先记录为后续建议                                                                                              |

## 风险与权衡

| 风险                                                                 | 等级 | 缓解                                                                                                                                       |
| -------------------------------------------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 解绑过度：把仍需在窗口级别生效的监听也解掉（如键盘重定向）           | 中   | 解绑只发生在 `dispose()`（该 Project 已关闭）路径；关闭后的旧工程本就不应再接收事件；回归用例断言「dispose 后旧工程不再收到 keydown 转发」 |
| 版本号漏掉某些变更方式（绕过 `updateReferences` 的原地修改）         | 中   | 版本号与索引重建同源（索引已有「引用+长度+首中尾采样」指纹自愈能力），并补一条「直接改 stage 数组后版本号递增」的用例                      |
| `OutlineWindow` 改为版本号后，纯文本编辑（不改结构）不再触发大纲刷新 | 中   | 大纲内容本质是结构（节点/连线关系）与标签；若确有影响，可在后续版本引入「内容修订号」，本轮先保证不回归既有结构刷新                        |
| D4 核验结果与猜测不符                                                | 低   | 无证据则不改，只登记                                                                                                                       |
