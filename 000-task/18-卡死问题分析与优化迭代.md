# 18 卡死问题分析与优化迭代

> 分析日期：2026-09-11
> 分析基线：`origin/master` @ `991be192`（本地 `a1909485` 快进到该提交后）
> 约束：**不改变任何交互行为与视觉设计**，只做等价重写与时间复杂度优化

## 1. 问题现象

用户反馈"存在卡死的问题"。结合架构（见 [01](01-架构总览.md)~[17](17-工程化与开发规范.md)），"卡死"在 Project Graph 里通常表现为两类：

| 类型                 | 典型场景                      | 表现                       |
| -------------------- | ----------------------------- | -------------------------- |
| 主线程长任务阻塞     | 打开/导入大工程、批量创建节点 | 界面完全无响应数秒到数十秒 |
| 每帧工作量随规模爆炸 | 大量节点时的悬停/渲染         | 帧率跌到个位数，操作迟滞   |

本轮聚焦**第一类**（真正意义上的卡死），并顺带清理第二类的重复计算。

## 2. 分析方法

按"架构解析 → 热点定位 → 复现 → 修复 → 回归验证"推进：

1. 从架构骨架入手：`Tab.loop()` 的 rAF 循环 → `Project.tick()` → 各 `Service.tick()`；舞台数据入口是 `Project.stage: StageObject[]`。
2. 搜索**算法级危险信号**：嵌套遍历、`while (true)`、每帧 `filter(instanceof)`、`stage.find` 线性查找。
3. 用**真实调用链**确认信号：谁在循环里调用它们（导入器、渲染器、鼠标交互、删除管理器）。
4. 建立**可复现的回归测试**（先 RED 后 GREEN），再改实现。

## 3. 根因清单（含证据）

### R1 `StageManager.updateReferences()` 的 O(实体 × 关系) 二重循环 —— 主因

旧实现：

```ts
for (const entity of this.getEntities()) {
  // O(E)，且每次 filter 全量数组
  if (entity instanceof ConnectableEntity) {
    for (const edge of this.getAssociations()) {
      // O(A)，且每个实体都重新 filter 一次
      if (edge instanceof Edge) {
        if (edge.source.unknown && edge.source.uuid === entity.uuid) edge.source = entity;
        if (edge.target.unknown && edge.target.uuid === entity.uuid) edge.target = entity;
      }
    }
  }
}
```

单次调用既是 `O(E×A)` 的循环，又额外产生 `E` 次全量 `filter`（`getAssociations()` 在循环体内）。

而 `StageManager.add()` 默认会对每次插入调用 `updateReferences()`：

```ts
add(stageObject: StageObject, skipUpdateReferences = false) {
  this.project.stage.push(stageObject);
  if (!skipUpdateReferences) this.updateReferences();
}
```

于是"逐条插入 N 个节点/边"的总代价是 `Σ O(k²) = O(N³)`。

**实测证据**（`StageManager.index.test.ts`，500 节点 + 499 边逐条 `add`）：

| 实现                | 端点访问次数（200 边场景） | 逐条 add 500 次耗时 |
| ------------------- | -------------------------- | ------------------- |
| 旧（二重循环）      | **40 600**                 | **9 813 ms**        |
| 新（hash 映射线性） | ≤ 800                      | **430 ms**          |

规模越大差距越大（立方 vs 平方），这正是"导入/打开大工程卡死"的直接原因。

### R2 导入器逐条 `add()`，未使用已有的 `skipUpdateReferences` 开关

`StageManager.add(obj, true)` 这个"跳过刷新"能力已存在，但以下批量导入路径都没用：

- `TreeImporter`（缩进树文本）
- `MarkdownImporter`
- `GraphImporter`（`nodeConnector.connectEntityFast` 内部固定 `add(newEdge)`）
- `MermaidImporter`（含 subgraph 嵌套，节点数可上千）

配合 R1，导入 N 行文本即 `O(N³)`。

### R3 `StageManager.get(uuid)` 为 O(N) 线性查找（原代码已标注 TODO）

```ts
get(uuid: string) {
  return this.project.stage.find((node) => node.uuid === uuid);
}
```

它被渲染热点 `Renderer.renderTags()` 每帧按标签数调用一次（源码注释已自嘲"这不成了 ON 方了？"），标签多时是每次 `O(T×N)`。

### R4 每帧/每次操作重复的"全量 filter + instanceof"取类型集合

`getEntities / getSections / getPenStrokes / getAssociations / getEdges / getConnectPoints / …` 全部是 `stage.filter(x => x instanceof X)`：

- `EntityRenderer.renderAllEntities()` 一帧内至少 6 次（实体、Section ×3、涂鸦）
- `MouseInteraction.updateByMouseMove()`（每次 `pointermove`）4 次
- `DeleteManager.deleteEntities()` 每删一个对象重新 `getEntities()` 一次 → 批量删除退化为 `O(N²)`

## 5. 实现要点

### 5.1 新增 `StageObjectIndex`（`app/src/core/stage/stageManager/StageObjectIndex.ts`）

一次性遍历舞台，按类型分桶并建立 `uuid → 对象` 映射：

- 桶：`entities / connectableEntities / associations / edges / lineEdges / crEdges / arcEdges / multiTargetUndirectedEdges / syncAssociations / sections / textNodes / imageNodes / connectPoints / urlNodes / penStrokes / svgNodes / latexNodes`
- 映射：`byUuid`（首个出现者优先，与原 `stage.find` 语义一致）、`entityByUuid`、`connectableEntityByUuid`

**关键设计：失效策略用"廉价指纹"而不是侵入式 hook。** 以 `数组引用 + 长度 + 首/中/尾三个位置的元素` 作为指纹，任一项变化即整体重建。这样：

- 走 `StageManager.add/delete`（`push` / `splice`）会自动感知；
- 绕过 StageManager 直接改数组的既有代码（`copyEngine` 的 `stage.push(...)`、`shortcutKeysRegister` 的 `stage.push` / `stage = []`、历史撤销的 `stage = deserialize(...)`、`stage.length = 0`）同样会自动感知。

**约束：分桶只依据"类型"这类静态属性。** 依赖运行时可变字段的过滤（如 `ImageNode.isBackground`）必须保留在调用方，否则索引会与真实状态不一致 —— 因此 `getConnectableEntity()` 是在桶上再做一次轻量过滤。

### 5.2 `updateReferences()` 线性化

先构建 `uuid → Entity`（首个优先），再单遍扫描关系解析 `unknown` 端点。语义与原实现完全等价，复杂度从 `O(E×A)` 降到 `O(E+A)`。

### 5.3 导入批量化

`TreeImporter` / `MarkdownImporter` / `GraphImporter` / `MermaidImporter` 改为 `add(obj, true)`，循环结束后统一调用一次 `updateReferences()`。`NodeConnector.connectEntityFast` 增加可选参数 `skipUpdateReferences`（默认 `false`，行为向后兼容）。

`MermaidImporter` 因为涉及 Section 嵌套，在**布局之前**额外补了一次 `updateReferences()`，以保证与"逐条插入"时布局阶段能看到的 Section 树一致。

### 5.4 批量作用域 `runBatch`（第二轮补充）

第一轮修完索引与导入器后，实测发现**逐条 `add()` 仍是 `O(N²)`**：

| 规模（N 节点 + N-1 边逐条 add） | 耗时     |
| ------------------------------- | -------- |
| 500                             | 460 ms   |
| 1 000                           | 1 750 ms |
| 2 000                           | 7 733 ms |

原因是每次 `add()` 都触发一次完整的 `updateReferences()`。同时实测单次刷新的成本是线性的（1 000 节点 4 ms / 5 000 节点 24 ms / 10 000 节点 36 ms），所以问题不在单次刷新，而在"一次用户操作里刷新了很多次"。

因此新增 `StageManager.runBatch(operation)`：作用域内 `add()` 不触发刷新，退出时统一刷新一次；嵌套时由最外层统一刷新；`finally` 保证异常路径也会刷新并把异常继续抛出。

应用到拆分文本节点路径（`textNodeSmartTools.keiOneTextNode`：k 个节点 + m×k 条连线）：

| 场景（N=2000 节点、k=60 次插入） | 耗时                 |
| -------------------------------- | -------------------- |
| 不用作用域                       | 250.7 ms             |
| 用作用域                         | **4.3 ms**（约 58×） |

规模越大收益越大（因为省掉的是 k 次 O(N) 刷新）。

第二轮同时推广到智能连线（`connectNodeSmartTools`）：

| 场景（1500 节点底图、选中 40 个节点做全连接，1560 条边） | 仅 `add()` 路径耗时 |
| -------------------------------------------------------- | ------------------- |
| 不用作用域                                               | 5 217.8 ms          |
| 用作用域                                                 | **8.2 ms**          |

> ⚠️ **重要更正（后来复测发现）**：上表的测量把 `historyManager` mock 掉了，因此只覆盖了 `add()`→`updateReferences()` 这条路径，**遗漏了 `connectEntity()` 内的 `historyManager.recordStep()`**。
> 真实路径中 `connectAll` 会调用 `recordStep` k² 次，每次都会全量 `serialize(stage)`，这才是真实卡死的主因。定量估算见 §5.9。

其中 `connectAll` / `connectDown` / `connectRight` / `insertNodeToTree` / `removeNodeFromTree` 的建边循环均已包裹；AI 建图工具（`BuiltInToolExecutors` 的 `expand_node`、`depth_expand_node`）的建节点+连线循环也已包裹（循环内只读碰撞箱与引用注册表，不依赖派生数据）。

**未改动的相关发现**：`StageManager.connectEntity()` 每条边都会 `historyManager.recordStep()`，因此在 `connectAll` 里会触发 k² 次全量 `serialize`，且每个边各自成为一个撤销步。这影响到“撤销粒度”这个交互语义，属于需要产品决策的改动，本轮不动（见 §7）。

**使用约束**（已写进方法注释）：作用域内部不能依赖 `updateReferences()` 维护的派生数据（`parentSection` / `topLevelEntities` / `rootSections` / 分组树）。拆分路径满足该约束（循环内只读连线与碰撞箱，派生数据在作用域结束后的 `layoutManager` 阶段才用）。

**与历史记录的交互（已核实）**：`runBatch` 只跳过 `updateReferences()`，**不跳过** `historyManager.recordStep()`。因此作用域内若发生 `recordStep`，快照会是"派生状态尚未刷新"的中间态。这不会造成问题：`parentSection` / `sectionDepth` / `nearestLockedAncestorSection` 三个派生字段**没有 `@serializable` 装饰器**（已核对 `StageEntity.tsx`），不进入快照；而撤销/重做时 `HistoryManager` 会主动调用 `updateReferences()` 重建它们。

### 5.5 作用域边界核查（刻意排除的调用点）

为避免把 `runBatch` 用错地方，逐个核查了受影响路径中"循环内的调用是否读派生数据"，结论如下：

| 检查项                                                | 是否读派生数据                                                            | 处置                                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `deleteAssociation()` → `isObjectBeLockedBySection()` | **是**：读 `nearestLockedAncestorSection`（由 `updateReferences()` 写入） | **不包裹**，保持每次删除后刷新                                           |
| `removeNodeFromTree` 的 `selectedNode.moveTo()`       | **是**：`moveTo` → `updateFatherSectionByMove()` 读 `parentSection`       | 该语句在 `runBatch` **之后**执行，作用域退出时已刷新（已按代码行号确认） |
| `graphMethods.isConnected()`（`connectEntity` 内）    | 否，读边桶（索引按指纹自愈）                                              | 可包裹                                                                   |
| `stageManager.isEntityExists()`（`isConnectable` 内） | 否，读 `byUuid` 索引                                                      | 可包裹                                                                   |
| `getOrCreateRef()`（AI 建图内）                       | 否，读 AI 引用注册表                                                      | 可包裹                                                                   |
| 拆分文本的 `layoutManager.alignTopToBottomNoSpace()`  | 读选中集合与图遍历                                                        | 在 `runBatch` **之后**执行                                               |

这张表是 `runBatch` 能安全推广的判断依据：凡是"循环内需要看到最新分组树/锁定状态"的调用点，一律不包裹。

### 5.7 索引指纹的一个已修复缺陷（自演化记录）

初版指纹只看“引用 + 长度 + 首元素 + 尾元素”。在写文档时我断言“现有代码的所有变更方式都会命中其中之一”，但**没有实测这个断言**。

实测（临时探针）发现反例：`stage[1] = b2`——长度 3 不变、首尾引用也没变，只有中间元素被换。此时索引**不会重建**，桶里仍留着旧对象 `b`、且缺少 `b2`，是真实的缓存不一致。

处置：

1. 指纹加入**中位采样**（`stage[length >> 1]`），封堵这类中间替换；
2. 把探针固化为永久回归用例（“中间元素被原地替换时索引也会重建”）；
3. 反向验证：把指纹退回“只看首尾”，该用例立即失败（第七道变异）；
4. 修正文档中过强的断言，并在 `StageObjectIndex` 注释里写明**残余边界**：理论上仍可用“长度、首、中、尾四项全同”的协同替换骗过索引。仓库内不存在这种写法（已全量检索：无 `stage[i] =`），若将来出现应改用显式版本号/增量通知，而不是继续加采样点。

这条记录保留下来，是因为它正是“自演化”该有的样子：**断言必须被测过，否则只是猜测。**

### 5.8 批量化的一个已知行为差异（有意保留）

`GraphImporter` 与 `MermaidImporter` 会在解析到非法行时 `throw`。批量化之后，末尾那次 `updateReferences()` 在抛错时不会执行，于是：

- 已插入的对象**仍在舞台上**（与改动前一致，本来也不是原子的）；
- 索引类查询（`getEntities` / `getAssociations` / …）**立即正确**，因为 `StageObjectIndex` 会按指纹惰性自愈；
- 但 `updateReferences()` 维护的派生数据（分组树、`topLevelEntities`、`rootSections`）会停留在抛错前的状态，直到下一次任何舞台变更触发刷新。

影响面：仅限"导入失败后、下一次操作前"的点击命中判定；框选与渲染不受影响，任意后续增删改都会恢复。

不额外加 try/finally 兜底，理由：该路径本身已是"部分导入 + toast 提示"的非原子语义，加兜底属于为低概率分支增加结构复杂度；如后续需要严格一致性，建议的做法是把导入改成"先在临时数组构建、成功后一次性合并"，而不是在异常路径打补丁。

### 5.9 历史记录的成本（实测 + 估算）

`HistoryManagerTimeEfficient.recordStep()`（默认模式 `timeEfficient`）每次都做一次 `serialize(整个 stage)`。用**真实序列化器**在 2999 个对象的合成舞台（1500 节点 + 1499 连线，`@serializable` 字段结构与 `TextNode`/`LineEdge` 对齐）上实测单次成本：

| 阶段            | 单次 serialize | 说明                                            |
| --------------- | -------------- | ----------------------------------------------- |
| 优化前          | 37.4 ms        | 其中 `Reflect.hasMetadata` 约 20.3 ms（占 54%） |
| 优化后（It-10） | 13.6 ms        | 约 2.75×                                        |

据此估算 `connectAll`（k=40 → 1560 条边 → 1560 次 `recordStep`）在 1500 节点工程上的历史开销：

| 阶段   | 估算总耗时 |
| ------ | ---------- |
| 优化前 | 约 58 秒   |
| 优化后 | 约 21 秒   |

（估算而非实测：本环境无法在不 mock 掉 UI 依赖链的前提下构造真实工程；合成舞台的 `details` 内容比真实工程轻，因此真实值可能更高。）

**结论**：序列化器优化把「每一次编辑」的历史成本降到约 1/2.75（对所有编辑都生效，不只是本轮的批量路径），但 `connectAll` 的 k² 次 `recordStep` 仍是真实卡死源。要彻底解决，必须落实「一次用户命令 = 一条历史」，这会改变撤销粒度（交互语义），需产品决策。

**代码内已有同类先例**：`StageManager.connectMultipleEntities()` 的注释明确写着「多重连接，只记录一次历史」，说明项目已经确立了这个意图；而 `connectAll` / `connectDown` / `connectRight` 循环调用 `connectEntity()`（每条边各记一次）与该意图不一致。

### 5.10 实测后判定不改：`deserialize` 的类级 `Reflect.hasMetadata`

`deserialize` 每个对象会做 3 次类级 `Reflect.hasMetadata`（`passExtraAtArg1` / `passObject` / `passExtraAtLastArg`），形式上与已优化的 `serialize` 同源，因此实测其占比：

| 指标                                           | 实测值         |
| ---------------------------------------------- | -------------- |
| 1500 节点全量 `serialize` + `deserialize` 往返 | 18.06 ms       |
| 类级 `hasMetadata` 单次成本                    | 0.0568 µs      |
| 按 9000 个对象 × 3 次估算                      | **约 1.53 ms** |

结论：绝对收益只有约 1.5 ms/次（对比 `serialize` 侧 `hasMetadata` 占 54%、省下 20 ms），属于"改动有收益但不划算"的区间。按仓库「最小够用、不做投机性扩展」的约定**不改**，仅登记数据，便于后续有人重做决策时有依据。

（`deserialize` 的主要成本在构造实例与 `replaceRef` 处理 `$` 引用，不在元数据查询。）

## 7. 后续迭代建议（按收益排序）

1. **历史记录粒度（需产品决策，数据见 §5.9）**：`connectEntity()` 每条边都 `recordStep()`，`connectAll` 因此有 k² 次全量 `serialize`（1500 节点、40 选中节点估算约 21 秒，是当前最大的剩余卡死源），并让每条边各自成为一个撤销步。项目内已有「多重连接，只记录一次历史」的先例（`connectMultipleEntities`），建议对齐；但这会改变撤销粒度（交互语义），需先确认。
2. **`runBatch` 继续推广**：`AutoComputeUtils`（仅按 x 键的调试模式触发）与 `textNodeSmartTools` 中剩余的循环 `add()` 可按同一约束包裹（需逐个确认作用域内不读派生数据）。已完成的推广见 §5.4。
3. **`updateReferences()` 的增量失效**：`runBatch` 虽能合批，但单次刷新仍是全量 O(N)。可让索引支持增量插入/删除，使刷新降为增量。
4. **逐帧工作量分层**：给渲染层提供“只读桶引用”访问器，省掉每帧的数组拷贝。
5. **`getConnectableEntity()` 的背景图过滤**：可改为维护一个"背景图集合"，避免每次调用都对可连接实体做一遍过滤。
6. **大工程基准数据集**：把 5k/10k 节点的 `.prg` 固化为基准样例，跑端到端打开耗时回归。
